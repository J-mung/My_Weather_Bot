### 배경

현재 북마크 화면에서는 카드 형태의 날씨 정보를 제공해주고 있다.

이때 렌더링 되는 카드 당 4번의 API 호출 비용이 발생한다.

- `ULTRA_NOW`: 현재 기온
- `ULTRA_FORECAST`: 기상 상태(하늘상태, 낙뢰 등)
- `SHORT_FORECAST`: 시간대별 기온
- `TODAY_TEMP_RANGE`: 금일 최저/최고 기온

이는 메인 화면에서 사용하는 날씨 훅(`useWeatherSummary`)를 그대로 활용하고 있기 때문이다.

문제는 새로고침, 화면진입 등과 같이 화면이 렌더링될 때마다 API를 호출하는 것이다.

최대 6개의 북마크를 생성할 수 있으므로 **최대 24번의 API 호출이 발생한다.**

서버가 없는 환경임을 고려해도 극단적으로 많이 호출하는 상황이라 판단하여 개선하고자 한다.

### 문제 정의

현재 구조에서는 `useWeatherSummary`을 그대로 활용하는 점이 가장 문제이다.

메인 화면에서는 각종 정보를 출력해주는 주력 화면이다.

```txt
1. 현재 기온
2. 기상 상태
3. 금일 최저/최고 기온
4. 습도
5. 시간대별 기온 및 기상 상태
```

북마크 화면은 요약 정보만 필요하지만, 상세 화면 수준의 API 호출이 발생하므로
카드 1개당 4회, 최대 24회의 API 호출이 발생한다.

서버가 없는 구조임을 감안하더라도 이 정도 호출량은 과도하며 동일 요청 반복도 제어되지 않는다.

### 변경 목표

이번 변경의 목표는 북마크 화면의 API 호출 비용 축소이다.

다음의 두 가지를 우선해서 진행해야 한다.

1. 북마크 전용 날씨 조회 훅을 생성한다.
2. 동일한 좌표(nx, ny), 동일한 발표 시각(base_date, base_time)에 대한 API 요청은 캐시를 적용해서 대신 응답한다.

### 변경 방향

#### 1. 북마크 전용 날씨 조회 훅을 생성한다.

원인:

- 메인 화면에서 사용하는 날씨 조회 훅을 그대로 사용하고 있다.
- 북마크에서는 필요치 않은 데이터도 API로 요청하고 있다.

변경:

- 북마크에서 필요한 데이터만 호출할 수 있게 훅을 새로 생성한다.

효과:

- 카드 별로 호출 API 비용이 4개에서 2개로 줄어든다.

AS-IS:

- `ULTRA_NOW`: 현재 기온
- `ULTRA_FORECAST`: 기상 상태(하늘상태, 낙뢰 등)
- `SHORT_FORECAST`: 시간대별 기온
- `TODAY_TEMP_RANGE`: 금일 최저/최고 기온

TO-BE:

- `ULTRA_NOW`: 현재 기온
- `TODAY_TEMP_RANGE`: 금일 최저/최고 기온

#### 2. 조회 데이터에 캐싱을 추가한다.

원인:

- 기상청 API는 새로운 예보 데이터를 응답해주는 데에 특정 시간대가 존재한다.
- 따라서 동일한 좌표(nx, ny), 동일한 발표 시각(base_date, base_time)에 대해선 동일한 데이터를 응답 받는다.

변경:

- TanStack Query로 메모리 캐시를 지정한다.
- localStorage로 캐시를 지정한다.

효과:

- 로딩/에러/동기화 관리 용도의 캐시 데이터가 생성된다.
- 브라우저 재진입 후에도 upstream을 방지할 영속성이 보장된다.

### 기대 효과

이번 변경이 적용되면 다음 결과를 기대할 수 있다.

1. API 호출 비용 감소

- 북마크 전용 날씨 훅을 만드는 것만으로 API 호출 비용이 약 50% 감소한다.
- 동일한 요청에 대해서 캐시로 응답하므로 API 호출 비용은 더 큰 폭으로 감소한다.

2. 동일 요청 방지

- 북마크 화면 재진입/새로고침 시 동일 요청의 재호출 방지할 수 있다.
- 브라우저 재진입 이후에도 localStorage 기반으로 upstream 호출 억제 할 수 있다.

### 구현 범위

- 새롭게 생성
