### 배경

지역 검색 기능을 `Fuse.js` 단독 기반으로 강화하는 과정에서,
검색 후보 선정과 하이라이트 처리 모두를 Fuse 결과에 최대한 정합적으로 맞추려는 시도를 진행했다.

이 과정에서 다음과 같은 문제가 확인됐다.

- 사용자가 기대하는 수준보다 후보군이 넓게 남는다.
- 검색 결과 하이라이트가 과도하게 표시된다.
- 검색 품질과 화면 표시 품질을 같은 기준으로 맞추기 어렵다.

이 문서는 `Fuse` 단독 사용 시 실제로 드러난 문제와 그 원인을 정리하기 위한 기록이다.

### 시도한 방향

1. 검색 후보 선정에 Fuse를 사용한다.
2. 하이라이트도 Fuse의 `matches.indices`를 그대로 사용한다.
3. 검색어는 정규화(`parseLocationText`)해서 검색 품질을 높인다.
4. 하이라이트는 `displayName` 또는 `fullName` 기준으로 표시한다.

즉, 검색 결과와 하이라이트 모두를 가능한 한 Fuse 결과에 정합적으로 맞추려는 방향이었다.

### 확인된 문제

#### 1. 후보군이 기대보다 많이 남는다

예:

- 입력: `서울특별시 동작구 노량`
- 기대: `서울특별시 동작구 노량진동` 위주로 좁혀짐
- 실제: `서울특별시 동작구 ...` 계열의 다른 후보도 함께 노출

원인:

- Fuse는 fuzzy search를 수행하므로, 입력 문자열과 유사한 후보를 폭넓게 남긴다.
- `threshold`가 너무 느슨하거나
  `ignoreLocation: true`로 설정되어 있으면 문자열 내 어느 위치에서든 매치가 쉽게 발생한다.
- 지역명처럼 구조가 정형화된 문자열에서도, 긴 입력에 대해 후보가 충분히 좁혀지지 않을 수 있다.

정리:

- `Fuse` 단독 사용은 짧은 입력에는 유리하지만,
  긴 입력에서 “정확히 좁혀지는” UX는 부족할 수 있다.

#### 2. 하이라이트가 과도하게 표시된다

예:

- 입력: `서울특별시 동작구`
- 결과: `서울특별시 동작구 동작동`
- 기대: 입력한 구간만 강조
- 실제: 문자열 전체 또는 필요 이상 넓은 범위가 강조됨

원인:

- `Fuse matches.indices`는 exact substring 위치라기보다,
  fuzzy match 결과에서 “관련 있다고 판단한 범위”를 제공한다.
- 검색어를 정규화한 상태에서
  공백이 포함된 `displayName`에 대해 fuzzy match를 수행하면,
  넓은 구간이 하나의 매치로 해석될 수 있다.
- 특히 `ignoreLocation: true`와 fuzzy 허용 범위가 결합되면,
  사용자가 기대하는 exact 하이라이트보다 넓게 칠해질 수 있다.

정리:

- `Fuse matches`는 하이라이트 근거로 활용할 수는 있지만,
  사용자가 기대하는 “입력 문자열 exact 강조”와는 다를 수 있다.

#### 3. 검색 정합성과 표시 정합성을 동시에 만족시키기 어렵다

검색 품질을 높이기 위해서는 보통 다음이 필요하다.

- 공백 제거
- 구분자 제거
- 소문자 변환
- fuzzy match

하지만 화면 하이라이트는 다음 조건을 만족해야 한다.

- 사용자에게 보이는 문자열 기준이어야 함
- 공백/구분자가 반영된 상태여야 함
- exact에 가까운 방식이 더 직관적임

즉,

- 검색은 정규화 문자열 기준
- 하이라이트는 표시 문자열 기준

이 되어야 하는 경우가 많아,
Fuse 단독으로 두 문제를 동시에 해결하기가 어렵다.

정리:

- 검색 엔진이 원하는 문자열 형태와
  화면 하이라이트가 요구하는 문자열 형태가 다를 수 있다.
- 이 때문에 “검색 정합성”과 “표시 정합성”을 완전히 동일 기준으로 유지하기 어렵다.

#### 4. `matches.indices` 구조를 그대로 처리하는 비용이 생각보다 크다

Fuse의 `matches.indices`는 단순 숫자 2개가 아니라,
여러 개의 `[start, end]` 튜플 배열로 반환될 수 있다.

예:

- 하나의 후보 문자열에 대해 여러 구간이 매치될 수 있음
- `"서울특별시 동작구"` 입력 시 두 개 이상의 매치 구간이 발생할 수 있음

이 경우 UI 렌더링에서는:

1. 모든 구간을 순회해야 하고
2. 문자열을 분할해야 하며
3. 구간이 겹치지 않게 처리해야 한다.

정리:

- `matches.indices` 기반 하이라이트는 이론적으로는 정합성이 높지만,
  코드 복잡도가 빠르게 올라간다.

### 실제 의사결정 포인트

Fuse 단독 사용을 유지할지 검토할 때 핵심 질문은 다음과 같았다.

1. 검색 결과의 fuzzy 정합성을 최우선으로 둘 것인가
2. 사용자가 이해하기 쉬운 하이라이트를 우선할 것인가
3. 긴 입력에서 후보를 더 강하게 좁히는 후처리를 허용할 것인가

검토 결과,
`Fuse` 단독만으로는 다음 두 가지를 동시에 만족시키기 어렵다고 판단했다.

- 긴 입력에서 충분히 좁혀지는 후보 목록
- 사용자가 기대하는 exact 하이라이트

### 결론

`Fuse.js`는 검색 후보를 빠르고 유연하게 찾는 도구로는 적합하다.
하지만 지역명 검색처럼 구조가 뚜렷한 문자열 검색에서는,
다음과 같은 한계가 확인됐다.

- fuzzy 결과가 과하게 넓게 남을 수 있다.
- 하이라이트 범위가 사용자가 기대하는 exact match와 다를 수 있다.
- 검색 품질과 표시 품질을 하나의 기준으로 맞추기 어렵다.

따라서 실제 UX 개선 단계에서는 다음 중 하나를 추가로 고려해야 한다.

1. `Fuse + 후처리 필터`
2. `Fuse + exact display 하이라이트`
3. `Fuse + 토큰 기반 하이라이트`

### 현재 적용한 보완 방향

최종적으로는 다음 혼합 방식을 채택했다.

1. 검색 후보 선정
- Fuse 기반 fuzzy search를 유지한다.
- 다만 긴 입력에서는 `exact > prefix > contains > fuzzy fallback` 우선순위로 후처리한다.
- 이를 통해 입력이 구체적일수록 후보군이 더 빠르게 좁혀지도록 한다.

2. 하이라이트
- Fuse `matches.indices`를 직접 화면에 사용하지 않는다.
- 화면 하이라이트는 `displayName` 기준 exact match로 처리한다.
- 이를 통해 사용자가 입력한 문자열이 어디에 대응되는지 더 직관적으로 보여준다.

정리:

- 후보 선정은 Fuse가 담당
- 하이라이트는 사용자 입력 기준 표시 로직이 담당

이 방식은 검색 품질과 표시 품질의 책임을 분리하여,
Fuse 단독 사용에서 드러난 과도한 후보 노출과 과한 하이라이트 문제를 완화한다.

### 한 줄 요약

`Fuse` 단독 사용은 검색 후보를 유연하게 찾는 데는 강하지만,
긴 입력에서의 후보 축소와 직관적인 하이라이트 UX까지 단독으로 해결하기에는 한계가 있다.
